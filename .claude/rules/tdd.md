> ⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**

---

## 프로젝트별 규칙 우선 조항

프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 지침이 있으면 **그 쪽이 우선**이다.  
이 파일은 프로젝트 규칙이 없을 때의 기본값(fallback)이다.

---

## 적용 기준

### TDD를 반드시 적용해야 하는 대상

- 비즈니스 로직 (계산, 변환, 상태 전이)
- API 핸들러 / 서버 엔드포인트
- 유틸리티 함수
- 버그 수정 — **버그를 재현하는 테스트를 먼저 작성한 뒤 수정한다**

### TDD가 불필요한 대상

- 타입 정의 (`.d.ts`, interface, type alias)
- 설정 파일 (vite, tsconfig, eslint 등)
- 순수 UI 컴포넌트 (로직 없는 렌더링만 하는 컴포넌트)
- SQL 마이그레이션 파일

## RED → GREEN → REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- **반드시 실행해서 실패를 눈으로 확인한다.** 머릿속으로 "당연히 실패하겠지"는 허용하지 않는다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류나 import 실패로 실패하는 건 RED가 아니다.

### GREEN

- **테스트를 통과시키는 최소한의 코드만 작성한다.**
- YAGNI — 지금 테스트가 요구하지 않는 코드는 쓰지 않는다.
- 신규 테스트뿐 아니라 **기존 테스트 전체가 통과하는지 확인한다.**

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **Green 상태를 유지한다.** 리팩터 중 테스트가 깨지면 즉시 되돌린다.
- **새로운 동작을 추가하지 않는다.** 추가하고 싶으면 다음 RED로 돌아가라.

### 반복

REFACTOR가 끝나면 **다음 동작에 대한 RED**로 돌아간다.

---

## 삭제 강제 규칙

테스트 전에 프로덕션 코드를 먼저 작성했다면 **삭제하고 RED부터 재시작한다.**

"참고용으로만 남겨두겠다"는 없다. 코드가 존재하는 순간 테스트 없이 작성된 코드다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트가 불필요하다" | 단순한 코드가 가장 자주 테스트 없이 방치되고, 나중에 복잡해진다. 지금 작성 비용이 가장 낮다. |
| "나중에 테스트를 추가하겠다" | 구현 후 테스트는 TDD가 아니다. 기존 동작을 깨는 변경을 잡아주지 못한다. |
| "시간이 없다" | 테스트 없이 작성한 코드를 디버깅하는 데 드는 시간이 더 길다. |
| "삭제하면 낭비다" | 테스트 전에 작성한 코드는 RED 단계를 건너뛴 코드다. 낭비가 아니라 규칙 위반이다. |
| "프로토타입이다" | 프로토타입이 프로덕션이 되는 경우가 대부분이다. 처음부터 TDD로 작성하는 게 빠르다. |
