# Commit 스킬

변경사항을 분석하고, 논리적 단위로 분류하여 한국어 커밋 메시지를 작성한다. 사용자가 확인한 뒤에만 실제 커밋을 실행한다.

## 절차

### 1단계: 변경사항 파악

```bash
git status
git diff HEAD
git diff --cached   # 이미 스테이징된 파일도 확인
```

변경된 파일 목록과 내용을 파악한다. 아직 스테이징되지 않은 파일도 포함해 전체 그림을 본다.

### 2단계: 논리적 단위로 분류

변경사항이 여러 관심사(concern)에 걸쳐 있는지 확인한다. 아래 기준으로 그룹을 나눈다:

- **하나의 기능 추가** → 커밋 1개
- **기능 추가 + 버그 수정** → 커밋 2개
- **기능 추가 + 스타일 변경 + 의존성 업데이트** → 커밋 3개
- 같은 파일이라도 변경 목적이 다르면 분리한다

> 판단 기준: "이 변경을 되돌릴 때 같이 되돌려야 하는가?" — 그렇다면 같은 커밋, 아니라면 분리.

### 3단계: 커밋 메시지 작성

각 단위에 대해 아래 형식으로 한국어 메시지를 작성한다:

```
<type>: <한국어 요약 (50자 이내)>

[선택] 본문: 왜 이 변경이 필요했는지, 어떤 문제를 해결했는지 설명
```

**타입 선택 기준:**

| 타입 | 언제 사용 |
|------|----------|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없이 코드 구조 개선 |
| `chore` | 빌드, 설정, 의존성, 문서 등 기능 외 변경 |
| `style` | 코드 포맷팅, 세미콜론 등 로직 변화 없는 변경 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서만 변경 |

**좋은 메시지 예시:**
- `feat: 사용자 프로필 이미지 업로드 기능 추가`
- `fix: 로그인 시 토큰 만료 오류 수정`
- `refactor: API 호출 로직을 훅으로 분리`
- `chore: eslint 규칙 업데이트`

**나쁜 메시지 예시 (피할 것):**
- `update` — 무엇을 업데이트했는지 알 수 없음
- `수정` — 타입 없음, 내용 불명확
- `asdfgh` — 의미 없음

### 4단계: 사용자에게 계획 제시

커밋 계획을 다음 형식으로 보여주고 승인을 요청한다:

```
커밋 계획:

1. feat: 다크 모드 토글 컴포넌트 추가
   파일: src/components/DarkModeToggle.tsx, src/hooks/useTheme.ts

2. chore: tailwind 설정에 dark 모드 활성화
   파일: tailwind.config.js

이대로 커밋할까요? (수정이 필요하면 말씀해주세요)
```

커밋이 1개일 때는 단순하게 제시한다.

### 5단계: 사용자 승인 후 커밋 실행

승인이 나면:

1. 해당 커밋에 포함할 파일을 `git add`로 스테이징
2. `git commit -m "..."` 실행
3. 여러 커밋이면 순서대로 반복

```bash
# 예시 (커밋이 2개인 경우)
git add src/components/DarkModeToggle.tsx src/hooks/useTheme.ts
git commit -m "feat: 다크 모드 토글 컴포넌트 추가"

git add tailwind.config.js
git commit -m "chore: tailwind 설정에 dark 모드 활성화"
```

커밋 후 `git log --oneline -5`로 결과를 확인하고 사용자에게 보여준다.

## 주의사항

- **절대로 사용자 승인 없이 커밋하지 않는다.** 4단계 제시 후 반드시 확인을 받는다.
- `.env`, 비밀키, 인증서 등 민감한 파일이 스테이징 대상에 포함되면 경고하고 제외를 권장한다.
- `git add -A` 나 `git add .` 대신 파일을 명시적으로 지정해 실수를 방지한다.
- 변경사항이 없으면 (`git status` 결과가 clean) 사용자에게 알린다.
